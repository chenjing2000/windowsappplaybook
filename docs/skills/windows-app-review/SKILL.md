# Windows 本地应用检查

## 工作流程

1. **确定范围与授权。** 从仓库 `AGENTS.md` 找到契约卡、专属检查和验证入口，确认只读审查或整改的授权，检查现有改动。缺少卡片时，查 README、规格与实际入口并标记不确定处。
2. **追踪入口与审查覆盖。** 专项沿受影响的用户入口查到状态、业务、存储及输出，核对直接调用方、失败路径与回归风险。全面审查覆盖主要用例，并检查职责与依赖、行为与数据兼容、状态与生命周期、失败与恢复、测试覆盖。
3. **分类发现。** 尽可能给出代码位置、触发条件、可观察影响和证据，区分正确性必修、可靠性与维护性建议、可选风格调整。不要把个人偏好或形式统一误报为缺陷。
4. **选择验证。** 使用项目契约卡中的真实命令和样本，按[运行形态与改动范围](../../../runtime-profiles.md)选择证据。使用隔离数据，避免覆盖用户数据。
5. **报告结果。** 记录主要发现、获准改动、实际命令和覆盖范围。分别标明通过、失败、跳过、超时及未验证事项。

## 审查清单

### 项目结构与文档

- 主体源码、测试、文档、工具、构建产物和发布产物是否按职责组织。
- 文档是否分类到 guides、reference、specs 等合适目录；是否存在无归属的临时文件。
- 根目录配置是否属于整个仓库；移动文件是否同步修正脚本、构建、CI 和相对路径。
- 不因缺少模板中的可选空目录而判定不合格。

### 技术选型与代码结构

- 技术方案是否符合项目契约；非默认技术是否有明确工程理由。
- 模块职责是否集中、依赖方向是否清楚、主要控制流和状态变化是否容易追踪。
- 按[第一性原理与最小必要设计](../../../design-framework.md#第一性原理与最小必要设计最高工程原则)优先检查：新逻辑是否只是绕过可以删除的旧规则；可否删除、合并或直接修改，而不是叠加状态、配置、分支或抽象；替代旧方案后是否清除了死代码与过时文档。
- 不以代码行数或抽象数量衡量质量；允许有助于理解的少量重复，避免重复维护同一业务规则。
- 高级语法以意图和行为是否更易理解与验证为判断依据，具体说明增加复杂性的地方。
- WPF 项目检查 View、ViewModel、业务规则与数据访问边界；不因未采用 MVVM 就自动判定为问题。

### Windows 11 UI

- 主窗口、子窗口、对话框、菜单、浮窗和控件是否保持一致的现代 Windows 视觉。
- 控件默认、悬停、按下、选中、禁用和键盘焦点状态是否清楚。
- 是否存在 DPI、窗口缩放、键盘导航、长文本裁切或主题方面的问题。
- 自定义窗口是否破坏拖动、最大化、还原、多屏和模态行为。
- 区分真实缺陷与项目有意采用的视觉例外。

### 依赖、运行环境与发布

- 是否区分系统级依赖、应用私有运行时和程序资源。
- 系统运行时是否检测版本并在缺失时提供合理提示；是否避免无必要重复安装系统级组件。
- 应用私有运行时是否放在约定目录并按版本管理；更新失败时是否保留可用旧版本。
- 发布方式是否符合项目契约。默认非自包含单文件和便携目录优先，但多文件或自包含发布可以有合理例外。
- 是否验证实际发布目录，而不只验证 IDE 开发环境。
- 发布或更新是否保护用户数据和仍在使用的运行时；是否可能清空整个应用目录。

### 用户数据与文件安全

- 默认用户数据是否位于可执行文件同级 `<AppName>/userdata/`；例外是否由用户确认并记录。
- 是否区分重要数据、普通数据、缓存、日志和临时文件。
- 重要数据是否在关键覆盖或迁移前备份；备份是否有保留策略和恢复方式。
- 迁移失败是否保护原始数据；是否存在静默回退、覆盖或删除风险。
- 临时文件是否有任务归属；清理是否只作用于本次任务拥有的文件。

### 行为、生命周期与错误处理

- 检查主要流程、失败路径、取消、重试、退出和资源释放。
- 不得静默改变业务行为或掩盖影响数据和结果的错误。
- 关注并发、异步旧结果覆盖新状态、重复启动及文件占用。
- 结合项目使用的[可复用模式](../../../patterns.md)检查。

### Git 与交付报告

- LLM 提供的 commit message 必须为英文，并描述实际变化。
- 重大节点验收后提供候选 commit message；实机验收未完成时必须明确标注未完成项。
- 默认不得代替用户执行 `git commit` 或 `git push`，除非用户明确授权。
- 报告应包含审查范围、发现及严重程度、证据、验证命令、通过/失败/跳过/未验证状态和已知限制。
